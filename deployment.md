# Deployment guide: Kirana Order

Live app: https://kirana-order.onrender.com (Render free tier; open it once and wait up to a minute if it has been idle)
Repository: https://github.com/Milandeep2004/kirana-order

## 1. Run locally

Requirements: Python 3.12 or newer, git.

```powershell
git clone https://github.com/Milandeep2004/kirana-order.git
cd kirana-order
python -m venv .venv
.venv\Scripts\Activate.ps1          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env              # macOS/Linux: cp .env.example .env
uvicorn app.main:app --reload
```

Open http://localhost:8000. The database (SQLite, `kirana.db`) is created and filled with
sample data on first start. Delete `kirana.db` to reset to the seed data. Do this after pulling updates that change the data model (for example, new columns): the app creates tables only when they do not exist yet.

Run the tests: `python -m pytest -q`

## 2. How it is deployed

A single web service on Render (free plan), described in `render.yaml`:

- Build: `pip install -r requirements.txt`
- Start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- Health check: `/health`
- Database: SQLite file on the service disk, seeded on start.

Steps: create a Render account, choose New > Blueprint, connect the GitHub repository, apply.
Render reads `render.yaml`, builds, and gives a public https URL.

### Environment variables (names only; values are never committed)

| Name | Purpose |
|---|---|
| `SECRET_KEY` | Signs session cookies. Generated by Render. |
| `DATABASE_URL` | Database location (SQLite file by default). |
| `DEMO_MODE` | `1` enables the fixed demo login code. Fake data only. |
| `DEMO_OTP` | The demo login code used when `DEMO_MODE=1`. |
| `COOKIE_SECURE` | `1` makes the session cookie HTTPS-only (set on Render). |
| `ANTHROPIC_API_KEY`, `LLM_MODEL` | Optional LLM tiebreaker for AI capture. Empty means rules only. |

## 3. Demo logins (for the reviewer)

Open the app and tap an account card on the login screen; no code is needed. You can also type
a registered number below the cards. The demo code `123456` is prefilled.

| Role | Phone | Notes |
|---|---|---|
| Retailer | 9000000001 | Sharma General Store. Knows its own wording ("biscuit chhota"), so the AI is surer for this shop. |
| Retailer | 9000000002 | Gupta Kirana. Tight credit limit: a larger order goes on hold for the desk. |
| Retailer | 9000000003 | Verma Super Mart. Best price tier. |
| Order desk | 9000000100 | Queue, edit, release holds, confirm, Tally export, van loading list, shops with no order in 14 days. |

Two more seeded shops (9000000004 Agrawal Provision, 9000000005 Tiwari Stores) have no recent
order, so they appear in the desk's "Not ordering" tab. Their invented data is listed as an
assumption in the TDD.

Suggested walk-through: log in as Sharma, open "By message", paste
`bhaiya 5 peti biscuit chhota, 2 peti washing powder 1 kilo, chai patti 250 wala 1 peti`.
Tea is out of stock, so swap it to continue. Place the order, then log in as the desk to confirm
it and export the Tally CSV. Then open the "Van list" tab to see the confirmed cases to load
(free cases included). Try `3 peti biscuit` as Sharma: his order history makes the AI suggest the
75 g pack with "ordered this 2 times before. Please check."

## 4. Known limits of this deployment

- Free-tier instances sleep when idle, so the first request after a pause can take about a minute.
- SQLite on the free plan is not durable: data returns to the seed data when the service restarts
  or redeploys. This is acceptable for a demo and would be a managed Postgres in production.
- Demo mode publishes the login code on purpose. Never enable it with real data.
- OTP, SMS and WhatsApp are mocked.
